# MeisterAI: structured Apple Foundation Models diagnoses

MeisterAI passes a bounded diagnostic context to Apple Foundation Models: module,
current error evidence with stable IDs, Homebrew location, permission observations,
service state, latest module report, and previous repair attempt. Unknown observations
remain unknown. Historical errors must not override a healthy current result.

A diagnosis uses `meister.diagnosis/v1` with a cause, evidence references, missing
information, next check, action ID and parameters. The Python contract validator
rejects malformed responses, unknown evidence, unsupported actions and unsupported
parameters. Tool observations are read-only. Log content is untrusted data, including
text that looks like instructions to the model.

The repair catalog contains only `quicklook_cache_reset`, `restart_finder`, and
`restart_dock`; `none` means no supported repair can be justified. Commands are fixed
in the application, not generated by the model. Missing information or an already
failed repair requires further diagnosis. Execution still requires the existing
`AI_HEAL_EXECUTE=true` or `--ai-heal-execute` opt-in. A successful model response or
command exit alone does not establish that the original issue was fixed: the module
must pass its subsequent verification. Reports distinguish suggestions, execution,
verified fixes, and unresolved problems.

## Commands and routing

`MeisterAI ai --diagnose-only [focus]` produces a structured diagnosis without
executing a repair. `MeisterAI ai report` renders the saved factual report with
evidence references. Both CLI variants share the fixed action mapping and remain
suggest-only by default.

Set `FM_HEAL_MODEL` or `FM_DIAGNOSE_MODEL` in `~/.meister/config` to `system`, `auto`,
or `pcc`. `FM_HEAL_MODEL=auto` starts locally and can escalate an unresolved diagnosis
to PCC when no missing facts remain. `FM_DIAGNOSE_MODEL=system` is the default for
read-only diagnosis. Choose `system` to keep model inference on-device; explicit
`pcc` selects Private Cloud Compute. An automatic escalation can send the bounded
diagnostic context to PCC.

The helper's inner time budgets are 25 seconds for system inference and 40 seconds
for PCC. The CLI applies a hard outer deadline of 35 seconds for `system` and
80 seconds for `auto` or `pcc`. Availability, refusal, context limits, timeout and
other helper failures remain distinguishable from a valid diagnosis with action
`none`. The evaluation runner below independently enforces its own per-case timeout
and always selects `system`, irrespective of these configuration values.

## Evaluation

Run the offline harness from the repository root:

```sh
python3 scripts/evaluate-fm.py
```

This validates 14 canned reference responses against the production contract. It
checks fixture integrity and report generation; **it does not measure model quality**.
The fixtures contain sanitized historical patterns from `meister.log`,
`meister.log.1`, and `heal.log`, with explicitly labeled safety and positive controls.
They cover PATH versus missing Homebrew, unattended sudo, permission failures, stale
warnings, unavailable models, justified no-fix, three catalog actions, log prompt
injection, missing XProtect scan evidence, repeated failed repairs, and missing data.
They contain no private user logs and are not presented as verbatim log records.

To measure the actual on-device model, use a newly compiled helper matching this
checkout (an old installed helper may still emit the previous command format):

```sh
python3 scripts/evaluate-fm.py --live --helper /absolute/path/to/meister-fm \
  --timeout 60 --output /tmp/meister-fm-live.json
```

For a small live sample, append `--case brew_outside_path` (repeat `--case` for
multiple IDs), or use `--limit 3`. Case selection precedes the limit; unknown IDs
and nonpositive limits are rejected.

Every invocation explicitly selects `--purpose ai-heal --model system`. There is no
PCC fallback and no repair execution in this runner. Each case has its own timeout.
Missing helpers, timeouts and helper errors are recorded as failures. The artifact
contains per-case latency, helper exit/error category, schema validity, evidence
references, action correctness, diagnosis term matches and justified no-fix scores.
Term matching is a lightweight regression signal, not a semantic correctness proof;
manual review and more representative fixtures remain necessary before claiming an
improvement. The JSON artifact is written with mode `0600` and contains metrics,
not raw stderr. Validated generated diagnoses are included only with
`--include-responses`, for manual review on sanitized fixtures.

The default artifact path is `artifacts/fm-evaluation.json`. Use `--fixtures` for a
separate corpus or `--contract` to test another checkout's production validator.
A nonzero exit means at least one case failed (or the corpus was empty).

Repair outcomes are **unmeasured** by default. Optional `--outcomes outcomes.json`
accepts separately verified observations keyed by fixture ID:

```json
{
  "quicklook_cache": {
    "verified": true,
    "success": true,
    "evidence": "External test run identifier and observed module retest result"
  }
}
```

This imports external evidence; it never verifies or executes a repair itself.
Model claims of success are not accepted as outcome measurements. Offline harness
results must never be reported as live model accuracy or repair success rates.
